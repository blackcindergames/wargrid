## Construct and set up (before tick 0)
- `Simulation.new(blocked_cells, size)`: empty world. `simulation.gd`
- `MapData.create(map, seats) -> Simulation`: map, players, start units and supply sources in one call; the normal entry. `map_data.gd`
- `Skirmish.create(with_match, second_controller, factions, map_path, starts, seat_count) -> Simulation`: standard game on top of `MapData.create`, two seats unless `seat_count` says more (one team per seat; seats after the first take `second_controller`). `skirmish.gd`
- `add_player(player, credits, controller, team) -> Dictionary`: register a seat. `simulation.gd`
- `spawn(owner, position, kind, occupied) -> int`: add a unit, -1 if blocked. `simulation.gd`
- `add_supply_source(origin, boxes, footprint, delete_when_empty) -> int`. `simulation.gd`
- `replace_blocked_cells(cells) -> Dictionary`: terrain edit (map editor, tests). `simulation.gd`
- `remove_object(id) -> Dictionary`: delete a unit or building. Outside callers are tests and `scripts/debug/combat_workload.gd`; not a command, so never use it in a networked match. `simulation.gd`
- `start_match(players) -> Dictionary` / `begin_setup(players)`: begin the match (`ongoing`, or `setup` until every seat has chosen a faction). Only `Skirmish.create` (and tests) calls `begin_setup`; `setup_seat(player, faction)` (`simulation.gd`) is called from `MapData.create` and the `choose_faction` command, never from outside the folder. `simulation.gd`

## Commands in
- `issue_command(command) -> {ok, error}`: queue a command for its `tick`. `simulation.gd`
- Common fields: `tick`, `player`, `sequence` (ints; sequence must increase per player), `type`. A caller that wants the next number asks `last_sequence(player)` (below) and adds one; offline that is `SimPump.run_job`'s job when the job sets `stamp_sequence` (the offline driver does; online and lockstep commands carry their own `sequence`, and a pump job without one and without the flag is refused by the simulation), no counter exists outside the simulation. Payload fields per type (`_payload_fields`, `simulation.gd`):

| type | fields |
|---|---|
| move, attack_move | entity_ids, target |
| stop | entity_ids |
| gather | entity_ids, source_id |
| attack, enter | entity_ids, target_id |
| unload | target_id |
| build | builder_id, building_kind, origin |
| resume_build | builder_id, building_id |
| cancel_build | building_id |
| produce | building_id, unit_kind |
| cancel_production | building_id, production_id |
| set_rally | building_id, target |
| defence_attack | building_id, target_id |
| choose_faction | faction |

- `move`, `attack` and `attack_move` take an optional `group_speed` (bool, `false` is the same as absent; a non-bool value, or the key on any other command, is refused with "Invalid group_speed"). When true, every unit the order commands at its tick gets the entity key `group_speed`, the lowest kind `speed` among them, and moves no faster while its intent is still that order's; any later order to the unit removes the key (P7 BR8, 2026-11-22).
- After setup a command is the only way to change the game. Same-tick order is `tick`, `player`, `sequence` (`_command_before`, `simulation.gd`).

## Advance
- `step() -> void`: run one tick. `simulation.gd`
- `tick() -> int`: current tick. `simulation.gd`
- `match_over() -> bool`. `simulation.gd`
- `survivors() -> Array[int]`: every match player during faction setup, then the players that still own a victory building; empty without a match. Lockstep uses it to tell a defeated leaver from a live one. `simulation.gd`
- Lockstep no longer touches these in the game: the online driver posts each tick as a pump job, with the commands from `take(tick, quiet, survivors)`, and hands the job's note to `record(tick, issued)` and `finish_tick(tick, state, digest)`. `take` and `finish_tick` refuse out-of-order calls: `take` must be asked for the next tick (any other tick ends the lockstep as `ended_protocol`, quiet or not), and `finish_tick` must send the next own frame (a gap or repeat ends it as `ended_protocol`); both do nothing once the lockstep has ended. `advance(sim)` composes `take`, issue, `record` and `step` for the headless client, the lockstep benchmark and the lockstep tests. `net/lockstep.gd`

## State out
- `snapshot() -> Dictionary`: `simulation.gd`. Keys: `tick`, `next_entity_id`, `entities` (sorted by id), `pending_commands` (sorted), `last_sequences`, `map`, `path_queue`, `players`, `buildings`, `sources`, `terrain_cells`, `next_production_id`, `command_results`, `combat_events`, `match`, `rng`, and `crates` and `chases` (sorted list of `{id, resume}`) when any exist. New simulation state goes in the snapshot, or a mirror test cannot see it diverge. Bot memory is not in it on purpose: in a lockstep match each client runs only its own seat's bot, so hashing it would desync the clients. Copies, except `entities[].route`, `map` and `terrain_cells`: those are shared read-only arrays (`simulation.gd` `_entity_copy`, `grid_navigation.gd` `snapshot`, `simulation.gd` `_terrain_snapshot`), so duplicate them before mutating. Since the view rows (2026-11-12) the game scenes no longer call it for input: orders and the HUD read the last `view_state()` the screen shows, and the snapshot is taken only at match start (camera reset, lockstep start), when the playtest match record is saved at the end, and on lockstep hash ticks.
- `match_stats() -> Array[Dictionary]`: one new row per player in ascending id order, `{player, units_built, units_lost, buildings_lost}`. `units_built` counts produced units (a quantity order counts its quantity; start, completion and rebuild units do not); `units_lost` and `buildings_lost` count combat, defence, transport-release and tunnel-bury deaths (completed buildings only, never rebuild holes, cancels or `remove_object` itself). Not in the snapshot, never hashed: display only; two clients and a replay agree because the counters follow the same ticks. `simulation.gd`
- `bot_state() -> Dictionary`: what the skirmish bot reads. `simulation.gd`. Keys `tick`, `entities` (id order; rows with `id`, `owner`, `kind`, `position`, `hp` (integer, as in `snapshot()`; the bot compares a wave's hit points between its own decisions), `combat` `{mode, target_id}` or null, and `hole_id` / `container_id` when present), `buildings`, `players`, `last_sequences`, with the same values as in `snapshot()`. Copies, built per call, not state, never hashed.
- `view_state() -> Dictionary`: what drawing, the HUD and sound read once per tick, without a full snapshot. `simulation.gd`. Keys `tick`, `map`, `players`, `buildings`, `sources`, `match`, `command_results`, and `crates` when any exist, with the same values as in `snapshot()`; `units`, a `ViewRows` (`view_rows.gd`) with one row per unit in id order. Built fresh on every call, so a held one keeps its values; it changes nothing in the simulation. Not a state fingerprint: never hash it or put it in a desync report.
- `ViewRows` (`view_rows.gd`): equal-length columns, row `i` is one unit. `PackedInt32Array`: `id`, `owner`, `kind` (index into `kinds`, a `PackedStringArray` built per call), `hp`, `max_hp`, `target` (`combat.target_id`, -1 for none), `queue` (`collection.target_id` while `collection.phase` begins with `waiting_`, else -1). `container` (`container_id`, -1 when the unit is not inside one). `PackedFloat64Array`: `x`, `y` (`position`), `heading_x`, `heading_y` (`heading`, default `[1.0, 0.0]`), `order_x`, `order_y` (`order.target`, 0.0 without an order). `PackedByteArray`: `status` (index into `ViewRows.STATUSES`, 255 for another value), `tier` (`combat.tier`, 0 without combat), `mode` (index into `modes`, `ViewRows.NONE` = 255 without combat), `phase` (index into `phases`, `NONE` without collection), `flags` (`HORDE`: `combat.horde > 0`; `CONTAINED`: has `container_id`; `HOLE`: has `hole_id`; `ATTACKING`: `combat.mode == "attack"`; `ORDERED`: `order != null`; `WAITING_SOURCE`: `collection.phase == "waiting_source"`; `COLLECTING`: `collection.enabled`). `kinds`, `modes`, `phases` are `PackedStringArray`s built per call: a `kind`, `mode` or `phase` index is valid only with the same rows object's own table, so code holding rows from two ticks (the sound director) compares strings or looks up through each rows' own table, never indices across rows objects. `index_of(id) -> int` (binary search, -1 if absent). `ViewRows.from_units(units)` builds the same rows from snapshot entities in id order (tests, labs). A field the presentation needs per tick that is not a column becomes a new column in the same change, never a per-unit Dictionary again.
- `StateHash.digest(snapshot) -> String`: the only state fingerprint. `state_hash.gd`
- `last_sequence(player) -> int`: the sequence of the last command of that player the simulation accepted, -1 if none (also in the snapshot as `last_sequences`). `simulation.gd`
- `set_hash_ring(enabled) -> void`: the ring below is on by default; the offline driver turns it off at creation, since the ring costs a full entity walk per tick; offline rows are taken every 30 ticks through `tick_hash()` instead. While off, `step` skips the hash and `hash_ring()` returns no rows; the digest and the snapshot do not change. `simulation.gd`
- `tick_hash() -> String`: the live hash of the current tick as 16 hex characters, the same value a `hash_ring()` row holds for that tick, computed on demand whether or not the ring is on. Reads state only. The offline driver records it every 30 ticks as the session record's `tick_hashes` (`"<tick>\t<16 hex>"` rows). `simulation.gd`
- `hash_ring() -> PackedStringArray`: the last 64 per-tick hashes of live state (`"<tick>\t<16 hex>"`, oldest first). Not in the snapshot: for desync reports only; a differing row is the first tick a hashed field differs. Hashed fields and the unhashed-state caveat: [guide chapter 10](../guide/10-determinism-and-replays.md). Never compare it across builds of different engine versions. `simulation.gd`

## Pump (screen side)

`SimPump` (`scripts/match/sim_pump.gd`, not in `simulation/`) is the screen side's only holder of a `Simulation`; the drivers own one (`driver.pump`). Everything the screen needs leaves it as data, never as a live read. Inline only for now: `post` runs the job on the calling thread. Design: [sim boundary](../superpowers/specs/2026-11-15-sim-boundary-design.md).
- `SimPump.new(sim)`, `start() -> Note`: job 0 (no step). It warms every cache `Registry.cache_names()` lists and then freezes them, nested values included (`Registry.freeze_caches()` in `definitions/definitions.gd`, with `cache_keys()` and `frozen_state()` for tests; `reach_cache` holds `Combat.reach_of`) and the default map (`Skirmish.freeze_map()`), publishes the first slot, and fills `note.starts` with each seat's start cell.
- `Job`: `commands`, `bots` (seats whose bot runs), `step` (default true), `want_digest`, `want_ring` (SB4: the note carries `hash_ring()`), `want_tick_hash` (the note carries `tick_hash()` after the step), `want_log` (the note carries the command log), `want_bot_lines` (default false: the note carries `Skirmish.debug_lines(sim, bots)` after the step, read-only; the offline driver asks only while F3 is open), `stamp_sequence` (default false), `preview` (`{player, builder_id, kind, origin}`). `SimPump.run_job(sim, recorder, job, slot) -> Note` is a static function so a thread could call it: it issues the commands (a missing `tick` becomes `tick()`; a missing `sequence` becomes `last_sequence(player) + 1` only when `stamp_sequence` is set), runs `Skirmish.issue_opponents` for the bots, steps, then fills the note and, when given a slot, assigns a fresh `view_state()` into it.
- `Note`: `tick`, `over`, `survivors` (`survivors()` after the step), `events`, `results` (the step's `combat_events` and `command_results`, copied; a `shot` whose target is a building also carries `target_building`, that building's `view_state()` row after the step, so sound can still read its owner and centre when the building is gone by the next displayed view; a building killed in the very step it was hit has no row; only `post` jobs' notes carry it, never `query` notes), `issued` (`{command, ok, error}` per command), `bot_commands`, `preview` (`{kind, origin, ok, error, tick}`), `snapshot` and `digest` (only with `want_digest`), `ring` (only with `want_ring`), `tick_hash` (only with `want_tick_hash`, else empty), `log` (only with `want_log`: the recorded commands), `bot_lines` (only with `want_bot_lines`: one F3 line per bot seat that has decided, else empty), `starts`, `stats` (`match_stats()`).
- `Slot`: `tick` and `view` (a `view_state()`). Every job gets a new `Slot` that is never written after it is published, so a reader may keep one for as long as it likes. `post(job) -> bool` runs a job and files its note and slot (false after `stop()` or once the pump has failed; a `run_job` that returns null fails the pump, and the caller must treat a false result as "not run"); `drain() -> Array[Note]` hands back the pending notes and makes the newest slot `current()`, the one before it `previous()`; `query(job) -> Note` runs a job without touching the slots or the notes (it still works on a stopped pump, and a null result fails the pump); `record() -> Dictionary` is a query job that returns `tick`, `digest`, `match` and `commands` (the recorded command log); `busy()` is false; `stop()` ends posting.
- `failure() -> String`: why the pump failed, empty while it is healthy. Today one cause exists, a job or query that returned no note ("post job returned no note after tick N"); a stopped pump's refusal leaves it empty. It is read on the main thread only. The offline driver reads it after a refused `post`, a null `query`, `record` and finish and shows the freeze card; `record()` then returns the last shown tick with an empty digest.
- `live() -> Simulation` is a shortcut, not interface for screen code (`recorder()` is gone: `record()` returns the log): only `sim_pump.gd` may read the live simulation (`tools/test_sim_boundary.py`); the online driver reads state through jobs since SB4. Tests may use `driver.pump.live()` to build and check state.

## Events out
- `combat_events() -> Array[Dictionary]`, `command_results() -> Array[Dictionary]`: events of the last step. Live read-only views, cleared in place by the next step: copy to keep. Both also appear in the snapshot. `simulation.gd`

## Read-only queries
- `map_data() -> Dictionary`. `simulation.gd`
- `preview_build(player, builder_id, kind, origin) -> Dictionary`: placement check for the HUD. `simulation.gd`. The drivers call it (`request_preview`), at most once per step call, for the latest requested ghost position (online, on the last tick job of the call); the placement code never does.
- `team_of(player) -> int`. `simulation.gd`
- `occupied_cells() -> Dictionary`: called only inside the folder (`containers.gd`, `production.gd`); `spawn` uses it. `simulation.gd`
- `Skirmish.team_memory(sim, team) -> Dictionary`: a copy of the team's wave clock (`wave`, `due`, `prev`, `released_by`, `launched_at`, `objective`, `attacked_at`, `left_cost`, `left_units`, `joiners`); not in the snapshot, never hashed (bot memory stays out of the snapshot on purpose). `skirmish.gd`

## Not interface
- Every `_`-prefixed member. Known leaks: `scripts/debug/combat_workload.gd` and `movement_workload.gd` read and write sim privates (`_entities`, `_buildings`, `_pending`, `_next_entity_id`, `_replace_union`), and `scripts/net/headless_client.gd` `_test_hooks` writes `_sim._players`.
- Diagnostic counters, not interface (benchmarks and tests only): `combat_work`, `horde_checks`, `scan_chases`, `retaliations`, `navigation_builds`, `navigation_local_updates`, `allocation_calls`, `reserved_allocations` (allocations the last step served from the reservation map). `path_cells` (route cells the last step's path service charged). `simulation.gd`
- `next_random()`: sim-internal RNG step (`simulation.gd`). Called by `combat.gd`, `salvage.gd`, `horde.gd` inside the folder; the one outside caller is `tests/test_combat.gd` `test_rng_sequence`.

## Rule for tests (user, 2026-11-09)
New tests set up, command and check the game only through the sections above, plus static unit data from `definitions/`. In scene tests the live simulation is `driver.pump.live()`, a tick is `BaseScene.tick(main)` (`_physics_process`, then `_drain_notes`) and a direct change is shown with `BaseScene.publish(main)` (`game/tests/test_base_scene.gd`). Existing files that read `sim._x` are grandfathered in the allowlist of `tools/test_sim_boundary.py` and migrated only when touched for another reason. Why: a native or repacked core can then run the same tests.
