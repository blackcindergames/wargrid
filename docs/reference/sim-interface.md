## Construct and set up (before tick 0)
- `Simulation.new(blocked_cells, size)`: empty world. `simulation.gd`
- `MapData.create(map, seats) -> Simulation`: map, players, start units and supply sources in one call; the normal entry. `map_data.gd`
- `Skirmish.create(with_match, second_controller, factions, map_path, starts, seat_count, teams) -> Simulation`: standard game on top of `MapData.create`, two seats unless `seat_count` says more (one team per seat unless `teams` gives one per seat; seats after the first take `second_controller`; a seat missing from `factions` waits for its `choose_faction`). `skirmish.gd`
- `add_player(player, credits, controller, team) -> Dictionary`: register a seat. `simulation.gd`
- `spawn(owner, position, kind, occupied) -> int`: add a unit, -1 if blocked. `simulation.gd`
- `add_supply_source(origin, boxes, footprint, delete_when_empty) -> int`. `simulation.gd`
- `replace_blocked_cells(cells) -> Dictionary`: terrain edit (map editor, tests). `simulation.gd`
- `remove_object(id) -> Dictionary`: delete a unit or building. Outside callers are tests and `scripts/debug/combat_workload.gd`; not a command, so never use it in a networked match. `simulation.gd`
- `start_match(players) -> Dictionary` / `begin_setup(players)`: begin the match (`ongoing`, or `setup` until every seat has chosen a faction). Only `Skirmish.create` (and tests) calls `begin_setup`; `setup_seat(player, faction)` (`simulation.gd`) is called from `MapData.create` and the `choose_faction` command, never from outside the folder. `simulation.gd`

## Commands in
- `issue_command(command) -> {ok, error}`: queue a command for its `tick`. `simulation.gd`
- `check_command(command) -> String`: the error `issue_command` would answer, empty when it would accept; queues nothing and never changes `tick_hash()` or the digest (a build preview may bump the unhashed `navigation_builds()` counter). `simulation.gd`
- Common fields: `tick`, `player`, `sequence` (ints; sequence must increase per player), `type`. A caller that wants the next number asks `last_sequence(player)` (below) and adds one; offline that is `SimPump.run_job`'s job when the job sets `stamp_sequence` (the offline driver does; online and lockstep commands carry their own `sequence`, and a pump job without one and without the flag is refused by the simulation), no counter exists outside the simulation. Payload fields per type (`_payload_fields`, `simulation.gd`):

| type | fields |
|---|---|
| move, attack_move | entity_ids, target |
| stop | entity_ids |
| gather | entity_ids, source_id |
| attack, enter | entity_ids, target_id |
| unload | target_id |
| build | builder_id, building_kind, origin |
| resume_build | builder_id, building_id |
| cancel_build | building_id |
| produce | building_id, unit_kind |
| cancel_production | building_id, production_id |
| set_rally | building_id, target |
| defence_attack | building_id, target_id |
| choose_faction | faction |
| ping | target |

- `move`, `attack` and `attack_move` take an optional `group_speed` (bool, `false` is the same as absent; a non-bool value, or the key on any other command, is refused with "Invalid group_speed"). When true, every unit the order commands at its tick gets the entity key `group_speed`, the lowest kind `speed` among them, and moves no faster while its intent is still that order's; any later order to the unit removes the key (P7 BR8, 2026-11-22).
- `ping` is a teammate map ping: its `target` is checked as a move's is (`_validate_target`: two finite numbers inside the map; walkability is not checked, so a building's cell is fine), and an accepted ping changes nothing but `last_sequences` and its `command_results` row. No snapshot key: the presentation reads accepted pings from the result rows and their targets from the lockstep's `command_log()`.
- After setup a command is the only way to change the game. Same-tick order is `tick`, `player`, `sequence` (`_command_before`, `simulation.gd`).

## Advance
- `step() -> void`: run one tick. `simulation.gd`
- `tick() -> int`: current tick. `simulation.gd`
- `match_over() -> bool`. `simulation.gd`
- `survivors() -> Array[int]`: every match player during faction setup, then the players that still own a victory building; empty without a match. Lockstep uses it to tell a defeated leaver from a live one. `simulation.gd`
- Lockstep no longer touches these in the game: the online driver posts each tick as a pump job, with the commands from `take(tick, quiet, survivors)`, and hands the job's note to `record(tick, issued)` and `finish_tick(tick, state, digest)`. `take` and `finish_tick` refuse out-of-order calls: `take` must be asked for the next tick (any other tick ends the lockstep as `ended_protocol`, quiet or not), and `finish_tick` must send the next own frame (a gap or repeat ends it as `ended_protocol`); both do nothing once the lockstep has ended. `advance(sim)` composes `take`, issue, `record` and `step` for the headless client, the lockstep benchmark and the lockstep tests. `net/lockstep.gd`

## State out
- `snapshot() -> Dictionary`: `simulation.gd`. Keys: `tick`, `next_entity_id`, `entities` (sorted by id), `pending_commands` (sorted), `last_sequences`, `map`, `path_queue`, `players`, `buildings`, `sources`, `terrain_cells`, `next_production_id`, `command_results`, `combat_events`, `match`, `rng`, and `crates` and `chases` (sorted list of `{id, resume}`) when any exist. New simulation state goes in the snapshot, or a mirror test cannot see it diverge. Bot memory is not in it on purpose: in a lockstep match each client runs only its own seat's bot, so hashing it would desync the clients. Copies, except `entities[].route`, `map` and `terrain_cells`: those are shared read-only arrays (`simulation.gd` `_entity_copy`, `grid_navigation.gd` `snapshot`, `simulation.gd` `_terrain_snapshot`), so duplicate them before mutating. Since the view rows (2026-11-12) the game scenes no longer call it for input: orders and the HUD read the last `view_state()` the screen shows, and the snapshot is taken only at match start (camera reset, lockstep start), when the playtest match record is saved at the end, and on lockstep hash ticks.
- `match_stats() -> Array[Dictionary]`: one new row per player in ascending id order, `{player, units_built, units_lost, buildings_lost}`. `units_built` counts produced units (a quantity order counts its quantity; start, completion and rebuild units do not); `units_lost` and `buildings_lost` count combat, defence, transport-release and tunnel-bury deaths (completed buildings only, never rebuild holes, cancels or `remove_object` itself). Not in the snapshot, never hashed: display only; two clients and a replay agree because the counters follow the same ticks. `simulation.gd`
- `bot_state() -> Dictionary`: what the skirmish bot reads. `simulation.gd`. Keys `tick`, `entities` (id order; rows with `id`, `owner`, `kind`, `position`, `hp` (integer, as in `snapshot()`; the bot compares a wave's hit points between its own decisions), `combat` `{mode, target_id}` or null, and `hole_id` / `container_id` when present), `buildings`, `players`, `last_sequences`, with the same values as in `snapshot()`. Copies, built per call, not state, never hashed.
- `view_state() -> Dictionary`: what drawing, the HUD and sound read once per tick, without a full snapshot. `simulation.gd`. Keys `tick`, `map`, `players`, `buildings`, `sources`, `match`, `command_results`, and `crates` when any exist, with the same values as in `snapshot()`; `units`, a `ViewRows` (`view_rows.gd`) with one row per unit in id order. Built fresh on every call, so a held one keeps its values; it changes nothing in the simulation. Not a state fingerprint: never hash it or put it in a desync report.
- `ViewRows` (`view_rows.gd`): equal-length columns, row `i` is one unit. `PackedInt32Array`: `id`, `owner`, `kind` (index into `kinds`, a `PackedStringArray` built per call), `hp`, `max_hp`, `target` (`combat.target_id`, -1 for none), `queue` (`collection.target_id` while `collection.phase` begins with `waiting_`, else -1), `container` (`container_id`, a transport or a building such as a Tunnel Hub; -1 when the unit is not inside one). `PackedFloat64Array`: `x`, `y` (`position`), `heading_x`, `heading_y` (`heading`, default `[1.0, 0.0]`), `order_x`, `order_y` (`order.target`, 0.0 without an order). `PackedByteArray`: `status` (index into `ViewRows.STATUSES`, 255 for another value), `tier` (`combat.tier`, 0 without combat), `mode` (index into `modes`, `ViewRows.NONE` = 255 without combat), `phase` (index into `phases`, `NONE` without collection), `flags` (`HORDE`: `combat.horde > 0`; `CONTAINED`: has `container_id`; `HOLE`: has `hole_id`; `ATTACKING`: `combat.mode == "attack"`; `ORDERED`: `order != null`; `WAITING_SOURCE`: `collection.phase == "waiting_source"`; `COLLECTING`: `collection.enabled`). `kinds`, `modes`, `phases` are `PackedStringArray`s built per call: a `kind`, `mode` or `phase` index is valid only with the same rows object's own table, so code holding rows from two ticks (the sound director) compares strings or looks up through each rows' own table, never indices across rows objects. `index_of(id) -> int` (binary search, -1 if absent). `ViewRows.from_units(units)` builds the same rows from snapshot entities in id order (tests, labs). A field the presentation needs per tick that is not a column becomes a new column in the same change, never a per-unit Dictionary again.
- `StateHash.digest(snapshot) -> String`: the only state fingerprint. `state_hash.gd`
- `last_sequence(player) -> int`: the sequence of the last command of that player the simulation accepted, -1 if none (also in the snapshot as `last_sequences`). `simulation.gd`
- `set_hash_ring(enabled) -> void`: the ring below is on by default; the offline driver turns it off at creation, since the ring costs a full entity walk per tick; offline rows are taken every 30 ticks through `tick_hash()` instead. While off, `step` skips the hash and `hash_ring()` returns no rows; the digest and the snapshot do not change. `simulation.gd`
- `tick_hash() -> String`: the live hash of the current tick as 16 hex characters, the same value a `hash_ring()` row holds for that tick, computed on demand whether or not the ring is on. Reads state only. The offline driver records it every 30 ticks as the session record's `tick_hashes` (`"<tick>\t<16 hex>"` rows). `simulation.gd`
- `hash_ring() -> PackedStringArray`: the last 64 per-tick hashes of live state (`"<tick>\t<16 hex>"`, oldest first). Not in the snapshot: for desync reports only; a differing row is the first tick a hashed field differs. Hashed fields and the unhashed-state caveat: [guide chapter 10](../guide/10-determinism-and-replays.md). Never compare it across builds of different engine versions. `simulation.gd`

## Pump (screen side)

`SimPump` (`scripts/match/sim_pump.gd`, not in `simulation/`) is the screen side's only holder of a `Simulation`; the drivers own one (`driver.pump`). Everything the screen needs leaves it as data, never as a live read. Two modes (SB5a, branch `sim-boundary-sb5a`, not merged): **inline**, where `post` runs the job on the calling thread, and **worker**, where one thread runs every job. The worker is behind the environment switch `WARGRID_SIM_THREAD=1`, off by default, so no shipped build uses it. Design: [sim boundary](../superpowers/specs/2026-11-15-sim-boundary-design.md).

### Mode
- `mode() -> String`, fixed when the pump is created: `"worker"` (switch on, the build has the `threads` feature, and no pump has failed in this process), `"inline"` (switch off, or no threads), `"inline-fallback"` (switch on and threads, but an earlier pump failed in this process, so the process latch makes every later pump inline). Code that branches on the worker compares `== "worker"`, never `== "inline"`. `static worker_wanted() -> bool` is the test for the worker (switch, threads and latch); a forced test mode is checked before it. Both drivers pass it on as `sim_mode()`; the playtest header and the online desync report carry it as the `sim` field, and the F3 overlay's first line shows `Sim: worker`, `Sim: inline` or `Sim: inline (fallback)`.
- Every failure cause sets the process latch (below), including a failure from a test pump, so one failed pump makes the rest of the process inline.
- Test seams (tests, `debug/` tools and `benchmarks/run_worker_digests.gd` only): `SimPump.force_mode_for_test(mode)` (a forced mode wins over the switch and the latch), `reset_process_latch_for_test()`, `cap_for_test(n)` (a smaller queue cap), `gate_publish_for_test(semaphore, where)` (holds the worker at `"before_publish"`, between `run_job` and the lock, or `"inside_publish"`, after the note is appended and before the ready slot and the count; bounded by a `try_wait` loop), `frame_source` and `clock` (`Callable`s; the physics frame counter and `Time.get_ticks_msec`, replaced to test the stall clock), `live_workers()` (pumps whose thread started and was not joined, abandoned ones included), `stop_live_for_test() -> int`, `pump_counts()` (`worker`, `forced`, `fallback`, `inline`: how many pumps each branch of `mode()` made; `tools/run_tests.sh` prints it as `SIM PUMPS`). Constants: `MAX_QUEUED` 3, `STALL_FRAMES` 90, `STALL_MSEC` 3000, `WAIT_MSEC` 5000, `TIMING_CAP` 4000.

### Setup, jobs, notes
- `SimPump.new(sim)`, `start() -> Note`: job 0 (no step) runs on the caller in both modes. It warms every cache `Registry.cache_names()` lists and then freezes them, nested values included (`Registry.freeze_caches()` in `definitions/definitions.gd`, with `cache_keys()` and `frozen_state()` for tests; `reach_cache` holds `Combat.reach_of`) and the default map (`Skirmish.freeze_map()`), publishes the first slot and fills `note.starts` with each seat's start cell. In worker mode it then installs the error logger (debug builds), starts the thread and waits for its start signal, at most `WAIT_MSEC` (`stall: worker did not start`). A null job 0 fails the pump (`start job returned no note after tick N`), starts no thread, fills `current()` from the simulation on the caller and returns an empty note at the simulation's tick.
- `Job`: `commands`, `bots` (seats whose bot runs), `plan_bots` (default false: the bots' orders are only checked with `check_command` by a `PlanRecorder` and kept in `note.bot_commands`, never issued to the sim or the pump's record; the online driver sets it on every tick job, and only the host's job lists bot seats), `step` (default true), `want_digest`, `want_ring` (the note carries `hash_ring()`), `want_tick_hash` (the note carries `tick_hash()` after the step), `want_log` (the note carries the command log), `want_bot_lines` (default false: the note carries `Skirmish.debug_lines(sim, bots)` after the step, read-only; the offline driver asks only while F3 is open), `stamp_sequence` (default false), `preview` (`{player, builder_id, kind, origin}`). `SimPump.run_job(sim, recorder, job, slot, timing) -> Note` is a static function, and the one the worker calls: it issues the commands (a missing `tick` becomes `tick()`; a missing `sequence` becomes `last_sequence(player) + 1` only when `stamp_sequence` is set), runs `Skirmish.issue_opponents` for the bots, steps, then fills the note and, when given a slot, assigns a fresh `view_state()` into it. `timing` is an optional scratch dictionary for the job timing rows below; callers that do not measure leave it out.
- **Bot planning stays on the worker, stamping stays on main.** With `plan_bots`, the `PlanRecorder` and the bot state live where the job runs; its simulation reference never enters a job, note or slot. The note carries the accepted proposals in `bot_commands`. The online driver submits them to the lockstep when it handles that note in `drain` (`_finish_job`: `record`, then each bot command through `Lockstep.submit`, then `finish_tick`), and the lockstep gives them their `tick` (`_last_sent + 1`), `player` and `sequence`. A bot order decided in the job of note N therefore goes into packet N + input delay in both modes, however late the drain; worker mode only changes the wall-clock send delay. Offline bots are not planned: the job issues them to the pump's own recorder.
- `run_job` runs only through `_run_owned(job, slot)`, the one place a job runs (only `sim_pump.gd` may define it: `tools/test_sim_boundary.py`). It compares `OS.get_thread_caller_id()` with the pump's owner thread in every build: a mismatch calls `push_error` and queues the marker `owner thread` instead of a note. In a debug build a worker's job whose thread logged an error (`pump_logger.gd`, a `Logger` that counts errors per thread id) queues the marker `fault`; a release build detects no script error, so online the 30-tick digest is the backstop and offline there is none. The owner thread is the main thread until the worker starts, the worker while it runs, and the main thread again after a join.
- `Note`: `tick`, `over`, `survivors` (`survivors()` after the step), `events`, `results` (the step's `combat_events` and `command_results`, copied; a `shot` whose target is a building also carries `target_building`, that building's `view_state()` row after the step, so sound can still read its owner and centre when the building is gone by the next displayed view; a building killed in the very step it was hit has no row; only `post` jobs' notes carry it, never `query` notes), `issued` (`{command, ok, error}` per command), `bot_commands`, `preview` (`{kind, origin, ok, error, tick}`), `snapshot` and `digest` (only with `want_digest`), `ring` (only with `want_ring`), `tick_hash` (only with `want_tick_hash`, else empty), `log` (only with `want_log`: the recorded commands), `bot_lines` (only with `want_bot_lines`: one F3 line per bot seat that has decided, else empty), `starts`, `stats` (`match_stats()`).
- `Slot`: `tick` and `view` (a `view_state()`). Every job gets a new `Slot` that is never written after it is published, so a reader may keep one for as long as it likes. **Payloads are plain data.** `Job`, `Note` and `Slot` hold only `int`, `float`, `bool`, `String`, `Dictionary`, `Array` and packed arrays, never a `Node`, `Resource`, `Callable` or `Signal`, because whichever thread drops the last reference runs the destructor; `tools/test_sim_boundary.py` (`impure_payload_fields`) checks the declared types of the three classes. The nested payloads it cannot see are known: `view.units` is a fresh `ViewRows` per job holding only packed columns, a standing preview request holds a `Vector2i` origin, a shot's `target_building` is that job's copied row. Views are compared by value (every `ViewRows` column); `StateHash.digest` is for snapshots only.

### Posting and reading
| Method | Caller | Inline | Worker |
|---|---|---|---|
| `post(job) -> bool` | main only | runs the job at once, files its note and slot; false after `stop()` or once a null result failed the pump | appends the job under the queue lock, counts it, wakes the worker; false, nothing queued, when stopped, failed, a failure marker is pending (read and set as the reason first) or `MAX_QUEUED` jobs are unpublished (the executing one plus the waiting ones). The caller treats false as "not run" |
| `has_room() -> bool` | main only | true (a smaller `cap_for_test` cap counts the notes not yet drained) | `unpublished < cap`; true when stopped or failed, so a failed pump never reads as full (its `post` still refuses). A false answer counts as a refusal in `queue_stats()`. Both drivers ask before they build a job or `take` a tick |
| `drain() -> Array[Note]` | main only | hands back the pending notes, newest slot becomes `current()`, the one before it `previous()` | the same, under the queue lock; then, outside it, the stall and dead-thread checks. Returns nothing on an abandoned pump, so a job that finishes late never reaches a driver |
| `query(job) -> Note` | main only | runs on the caller without touching slots or notes; a null result fails the pump | one queue entry with its own reply semaphore, never counted against the cap and never a drained note; main polls for the reply up to `WAIT_MSEC` and on a timeout abandons the pump (`stall: query waited 5000 ms`); null at once on a failed pump; runs inline once the pump is stopped and joined |
| `record() -> Dictionary` | main only | a query job returning `tick`, `digest`, `match` and `commands` (the recorded log) | the same through the worker, so it waits behind the queue; on a failed pump it returns the last shown tick, an empty digest and an empty log (the log only if the worker is gone) |
| `busy() -> bool` | main only | false | true while jobs are unpublished and the pump has not failed |
| `stop()` | main only | sets a flag; later posts return false | sets quit, drops the waiting jobs, wakes the worker and polls up to `WAIT_MSEC` for its exit acknowledgement; the running job finishes first (at most one job); it joins only after that acknowledgement, otherwise abandons the pump (`stall: stop waited 5000 ms`). Idempotent; returns at once on an abandoned pump |
| `live() -> Simulation` | main, tests, setup | the simulation | the simulation, but asserts in debug that the pump is not busy and not abandoned |

- `queue_stats() -> Dictionary` and `reset_queue_stats()` (zeroes them; the bench calls it at its window start). Keys: `posts_attempted` (accepted posts plus refusals), `room_refusals` (`has_room()` false answers), `refusal_streak_max` (longest run of consecutive `frame_source` frames with a refusal), `depth_max` (largest unpublished count right after an accepted post), `depth_at_cap_share` (share of accepted posts that left the queue at its cap), `queue_cap`, `main_wait_count`, `main_wait_total_ms`, `main_wait_max_ms` (main's waits in `query`, `stop` and the start handshake), `jobs` (one row per drained worker job, at most `TIMING_CAP`: `tag` `plain` or `snapshot+digest`, `job_usec` the `run_job` time, `handoff_usec` the end of the step to the end of `run_job`, `age_usec` the publish to the drain). Inline pumps produce no `jobs` rows.
- `live()` is a shortcut, not interface for screen code: only `sim_pump.gd` may read the live simulation (`tools/test_sim_boundary.py`); the online driver reads state through jobs. Tests may use `driver.pump.live()` to build and check state while the pump is idle.
- A worker never waits on main, except the test gate's bounded `try_wait`, and calls no `OS.has_feature`, `print` or `printerr`. The Profiler (`debug/profiler.gd`) is not thread-safe: `start()` in worker mode asserts it is off and nothing may enable it while a worker lives, so the ten Profiler cases of the scene suites run with inline pumps under the switch (`INLINE_UNDER_SWITCH` in `tests/run_tests.gd`).

### Failure
- `failure() -> String`: why the pump failed, empty while it is healthy; the first reason stays. Read on the main thread only. The worker never writes it: it queues a marker (`post`, `query`, `owner thread` or `fault`) that main turns into the reason at its next `drain`, `post` or `query`, and main itself finds the stalls and the dead thread. Every cause sets the process latch. A full queue and an ordinary `stop()` leave it empty. The reasons:
  - `start job returned no note after tick N`, `post job returned no note after tick N`, `query job returned no note after tick N` (a null result);
  - `fault: a job logged an error at tick N` (worker, debug builds), `owner thread: a job ran off its thread at tick N`;
  - `stall: job at tick N ran over 90 frames` (the oldest unpublished job: 90 physics frames and 3000 ms both elapsed; checked only while jobs are unpublished, so an idle pump, an open pause menu, a slow online peer or a suspended app is no stall), `stall: query waited 5000 ms`, `stall: stop waited 5000 ms`, `stall: worker did not start`;
  - `dead thread` (the worker is gone while jobs are unpublished).
- The tick in a text comes from the last slot main drained, so a marker read in `post` or `query` instead of `drain` can name a tick that lags by the number of undrained notes; text only.
- After a marker the worker drops the waiting jobs and exits, and `drain` returns no note from the failed job. After a stall main calls `_abandon(cause)`: quit set, the worker woken, the reason and the latch set, the pump marked abandoned. Nothing reads an abandoned pump again, and it is never joined while its worker may still run. The static `_threads` list keeps every pump with a started, unjoined thread alive (a `Thread`'s callable does not keep its `RefCounted` owner alive), and the next `start()` joins any abandoned pump whose worker has exited.
- The offline driver reads `failure()` after `drain()` (before its empty-notes return, because a stall produces no note), after a refused `post`, a null `query` and `record`, and shows the freeze card. The first failure also clears the placement and the selection (`match_screen._clear_on_first_failure`), offline only. The online driver reads it too (`driver.failure()` passes it on): in `step` it stops before `take` when a failure is set or the pump has no room; on a failure it ends the lockstep with `sim pump failed: <reason>` unless the lockstep already has an earlier end (a relay loss seen first stays the reason) and closes the transport in that frame, so the peer sees the seat leave. That close is made twice, in `_end_on_failure()` and again in `_finish()`; `RelayTransport.close()` calls the socket's `close()` each time, and the second call on an already closing `WebSocketPeer` is an engine no-op (not re-checked here), so the peer sees one leave. A failure at startup (a null job 0 or start query) ends the match before any packet is sent.
- Known limit, observed on macOS only (CI runs the fault cases on Linux and Windows in its `Pump fault processes` step, first run owed at the gate): an abandoned worker still inside a job when the process exits can abort Godot at teardown (a use-after-free of freed script bytecode; in a probe 7 to 9 of 10 runs per stall case exited cleanly). The gate's fault cases wait for the worker to exit first. Whether SB5a must make quit-after-a-stall safe is an open owner question ([verification](sim-boundary-verification.md#sb5a)).

### Online record and the leave
- An online match's saved playtest record has two sources: its command lines come from `driver.match_log()` (`Lockstep.command_log()`, filled by `Lockstep.record`, called from `_finish_job` and `_stop_pump`) and its end tick and digest from `driver.record()` (`pump.record()`). A job that ran but was not drained would change the digest while its commands are missing from the log, so online `stop()` and `_finish()` after a lockstep end (`_stop_pump`) stop the pump and then, only when `pump.failure()` is empty, take the completed notes through the pairing guard (`_paired_tick`) into `Lockstep.record` only (no bot submit, no `finish_tick`, nothing sent after the leave) and set the last note, so the log and the digest meet at the same tick. The commands of jobs the stop dropped are lost with the leave. Both drivers' `create` call `pump.stop()` on the old pump before they build the new simulation, so an old worker never runs beside the new match's warm-up and old notes never enter the new log.
- The pairing guard (`_paired_tick`): while no tick is taken, a note that did not advance the tick is harmless (a test publish); one that advanced it ends the match with a protocol error before anything is recorded, and so does a note whose tick is not its taken tick plus one.

## Events out
- `combat_events() -> Array[Dictionary]`, `command_results() -> Array[Dictionary]`: events of the last step. Live read-only views, cleared in place by the next step: copy to keep. Both also appear in the snapshot. `simulation.gd`

## Read-only queries
- `map_data() -> Dictionary`. `simulation.gd`
- `preview_build(player, builder_id, kind, origin) -> Dictionary`: placement check for the HUD. `simulation.gd`. The drivers call it (`request_preview`) for the latest requested ghost position: while a request stands, every tick job carries it, offline and online, and the last answered preview wins; the placement code never calls it.
- `team_of(player) -> int`. `simulation.gd`
- `occupied_cells() -> Dictionary`: called only inside the folder (`containers.gd`, `production.gd`); `spawn` uses it. `simulation.gd`
- `Skirmish.team_memory(sim, team) -> Dictionary`: a copy of the team's wave clock (`wave`, `due`, `prev`, `released_by`, `launched_at`, `objective`, `attacked_at`, `left_cost`, `left_units`, `joiners`); not in the snapshot, never hashed (bot memory stays out of the snapshot on purpose). `skirmish.gd`

## Not interface
- Every `_`-prefixed member. Known leaks: `scripts/debug/combat_workload.gd` and `movement_workload.gd` read and write sim privates (`_entities`, `_buildings`, `_pending`, `_next_entity_id`, `_replace_union`), and `scripts/net/headless_client.gd` `_test_hooks` writes `_sim._players`.
- Diagnostic counters, not interface (benchmarks and tests only): `combat_work`, `horde_checks`, `scan_chases`, `retaliations`, `navigation_builds`, `navigation_local_updates`, `allocation_calls`, `reserved_allocations` (allocations the last step served from the reservation map). `path_cells` (route cells the last step's path service charged). `simulation.gd`
- `next_random()`: sim-internal RNG step (`simulation.gd`). Called by `combat.gd`, `salvage.gd`, `horde.gd` inside the folder; the one outside caller is `tests/test_combat.gd` `test_rng_sequence`.

## Rule for tests (user, 2026-11-09)
New tests set up, command and check the game only through the sections above, plus static unit data from `definitions/`. In scene tests the live simulation is `driver.pump.live()`, a tick is `BaseScene.tick(main)` (`_physics_process`, then `_drain_notes`) and a direct change is shown with `BaseScene.publish(main)` (`game/tests/test_base_scene.gd`). Existing files that read `sim._x` are grandfathered in the allowlist of `tools/test_sim_boundary.py` and migrated only when touched for another reason. Why: a native or repacked core can then run the same tests.
